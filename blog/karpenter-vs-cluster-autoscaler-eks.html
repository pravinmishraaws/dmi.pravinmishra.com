Karpenter vs Cluster Autoscaler: Node Autoscaling on EKS

By Pravin Mishra

In the last post, we covered how to keep a cluster current without turning an upgrade into an incident. Once the cluster is running, another operational question shows up fast: how does it get more worker-node capacity when workloads actually need it? Traffic isn't constant — an HPA might scale an app from two pods to twenty during a spike, a rollout might create extra pods temporarily, or someone might bump replicas for a load test. Those extra pods still need somewhere to run, and that's the problem node autoscaling solves. On EKS, two tools come up constantly: Cluster Autoscaler and Karpenter. Both add capacity when pods can't be scheduled, but they work in genuinely different ways.

What happens without node autoscaling

When the scheduler can't place a pod — no node has enough CPU or memory available — the pod sits in Pending. That's not just a status; it means the application doesn't have the capacity it needs right now. If an app needs more pods during a traffic spike and those pods can't schedule, requests queue, response times climb, and users feel it directly. Without node autoscaling you're choosing between two bad options: over-provision for peak traffic and pay for capacity that sits idle most of the time, or under-provision and scramble to add nodes exactly when the application needs them most. Node autoscaling exists to take that trade-off off the table.

Cluster Autoscaler — the original approach

Cluster Autoscaler is the original Kubernetes node autoscaler, and on EKS it works with AWS Auto Scaling Groups. The idea is straightforward: your node group is backed by an ASG, and when Cluster Autoscaler sees a pod that can't be scheduled, it checks whether adding another node from that existing group would help. If yes, it raises the ASG's desired capacity, AWS provisions a new EC2 instance, the instance joins the cluster, and the scheduler places the pending pod. Scale-down runs the same logic in reverse — it looks for underused nodes, checks whether their pods can safely move elsewhere, and if so drains the node and shrinks the ASG.

Cluster Autoscaler works. It's stable, widely used, and still a completely valid option. Its real limitation is that it scales the node groups you already defined — which means you have to think about node group shapes in advance. If one workload needs more memory, another needs more CPU, and a third runs better on a different instance family, you typically end up creating those groups ahead of time. Cluster Autoscaler picks from the capacity shapes you already gave it; it doesn't design a new node shape per workload. For plenty of teams that's fine. For more dynamic workloads, it can mean too many node groups, too much upfront planning, or nodes that are bigger than the pending pods actually need.

Karpenter — provisioning from the pod up

Karpenter takes the opposite starting point. Cluster Autoscaler starts from the node groups you already created and asks which one to scale. Karpenter starts from the pods that can't be scheduled and asks what kind of node this workload actually needs — looking at CPU, memory, architecture, zones, taints, tolerations, affinities, and every other scheduling constraint, then provisioning a node that fits. It isn't bumping an ASG's desired count; for the nodes it manages, it provisions EC2 capacity directly against the workload's actual requirements. Instead of defining many fixed node groups upfront, you define the boundaries Karpenter is allowed to operate within — capacity types, instance families, zones, subnets, security groups, node IAM role — and Karpenter decides which instance type actually fits the pods waiting right now. That's why it's often the better fit for EKS platforms that need flexible, right-sized, cost-aware provisioning.

Two resources make this work: NodePool and EC2NodeClass. The short version — NodePool defines what Karpenter is allowed to create; EC2NodeClass defines how those EC2 nodes get created in AWS. The NodePool carries the scheduling and capacity rules:

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
        - key: kubernetes.io/os
          operator: In
          values: ["linux"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["3"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  limits:
    cpu: "100"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s

Don't worry about memorizing every field — the point is that the NodePool defines the boundaries: what kind of capacity Karpenter is allowed to create at all. The EC2NodeClass covers the AWS-specific details — which AMI, which subnets, which security groups, which node identity:

apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  amiSelectorTerms:
    - alias: al2023@v20240807
  role: KarpenterNodeRole-book-review
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: book-review
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: book-review

NodePool says what Karpenter is allowed to provision; EC2NodeClass says how those nodes get created in AWS. Karpenter combines both: when a pod goes Pending, it checks the pod's requirements, the NodePool's constraints, and the EC2NodeClass's AWS settings, then launches a suitable instance — no fixed node group required in advance. See the Karpenter getting started guide, the NodePool spec reference, and the EC2NodeClass spec reference for the full field list.

Karpenter's two IAM identities

If Karpenter is going to launch EC2 instances directly, it needs an AWS identity to do that with — and the instances it launches need their own identity once they exist. These are two separate roles solving two separate problems, and mixing them up is an easy first-setup mistake.

The Karpenter controller role is what the controller pod itself uses to call AWS APIs — launching instances, terminating them, discovering AMIs, reading cluster information, passing the node role when it creates a node. In this course, we use EKS Pod Identity for this: an IAM role assumable through the pods.eks.amazonaws.com service principal, with a Pod Identity association for the karpenter service account in the karpenter namespace.

resource "aws_iam_role" "karpenter_controller" {
  name = "karpenter-controller"

  assume_role_policy = jsonencode({
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "pods.eks.amazonaws.com" }
      Action    = ["sts:AssumeRole", "sts:TagSession"]
    }]
  })
}

resource "aws_eks_pod_identity_association" "karpenter" {
  cluster_name    = module.eks.cluster_name
  namespace       = "karpenter"
  service_account = "karpenter"
  role_arn        = aws_iam_role.karpenter_controller.arn
}

That's the role Karpenter uses to talk to AWS — but it's only half the picture. When Karpenter launches a new EC2 instance, that instance needs its own identity too, because the node has to join the cluster, talk to the control plane, pull images from ECR, and run the usual node-level components. That's the node role — you can use a dedicated Karpenter node role, or reuse the same minimum-permission pattern from the node groups post. The controller role answers "what is Karpenter allowed to do in AWS?"; the node role answers "what are the EC2 instances Karpenter launches allowed to do once they exist?" — different questions, different roles.

The EC2NodeClass is where you connect Karpenter to that node identity — either a role directly, or a pre-created instance profile:

resource "aws_iam_instance_profile" "karpenter_node" {
  name = "karpenter-node"
  role = aws_iam_role.karpenter_node.name
}
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  amiSelectorTerms:
    - alias: al2023@v20240807
  instanceProfile: karpenter-node
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: book-review
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: book-review

In a production setup, these IAM resources live in Terraform, while the Karpenter controller itself is deployed with Helm through your GitOps repository — Terraform prepares the AWS foundation, Helm deploys the Kubernetes-side application. That split — cloud infrastructure in Terraform, Kubernetes applications through Helm and GitOps — is deliberate, not incidental. See Karpenter IAM permissions for the full controller policy reference.

The bootstrap node group — solving Karpenter's chicken-and-egg problem

Karpenter is a controller pod — it runs inside your cluster. But it's also responsible for provisioning new nodes, and it needs a node to run on before it can provision anything. If the entire cluster depends on Karpenter for compute from the very start, there may be nothing available for Karpenter itself to run on.

The fix is a small, fixed bootstrap node group — a standard managed node group, often just two small nodes, running the stable platform layer of the cluster. Karpenter runs there, and depending on your setup, so do other critical components: CoreDNS, the AWS Load Balancer Controller, External Secrets, cert-manager, metrics-server. The bootstrap group isn't for application workloads — its entire job is keeping the cluster's core platform layer alive. A taint protects it from ordinary application pods:

managedNodeGroups:
  - name: bootstrap
    instanceType: t3.medium
    desiredCapacity: 2
    taints:
      - key: CriticalAddonsOnly
        effect: NoSchedule

CriticalAddonsOnly:NoSchedule means ordinary pods won't land there unless they explicitly tolerate it — your application pods shouldn't have that toleration, but Karpenter and the platform components you want on that group do. Many production setups add node affinity on top, so those components prefer or require the bootstrap group specifically. The resulting layout:

Cluster
├── Bootstrap Node Group
│   ├── Managed node group
│   ├── Fixed small capacity, for example 2 nodes
│   ├── Taint: CriticalAddonsOnly:NoSchedule
│   └── Runs: Karpenter, CoreDNS, AWS LB Controller, cert-manager, ...
│
└── Karpenter Nodes
    ├── Created dynamically
    ├── Scaled based on pending Pods
    └── Runs: application workloads

Managed node groups and Karpenter aren't either-or — they coexist by design. The managed group runs the stable system layer; Karpenter runs the dynamic application layer on top of it.

Consolidation — how Karpenter handles scale-down

Everything so far has been about scale-up — a pod goes Pending, Karpenter notices, Karpenter launches capacity. The other half of autoscaling is removing capacity once it's no longer needed, and Karpenter does that through consolidation: continuously checking whether the same workloads could run on fewer, better-packed, or cheaper nodes. If the NodePool's disruption settings allow it, Karpenter can drain a node and remove or replace it — and this isn't limited to empty nodes; depending on settings, it can also consolidate nodes that are still running pods but sitting underused.

disruption:
  consolidationPolicy: WhenEmptyOrUnderutilized
  consolidateAfter: 30s

consolidationPolicy controls what kind of nodes Karpenter is allowed to consolidate — WhenEmptyOrUnderutilized covers both empty and underused nodes. consolidateAfter controls how long Karpenter waits before acting; a value like 30s is aggressive, moving quickly once conditions are met. In production, many teams use a higher value, since bursty workloads can look briefly idle without actually being done — you don't want nodes replaced the moment traffic dips for a few seconds. Cluster Autoscaler can also remove underused nodes, but it stays tied to the ASGs and node groups you created; Karpenter's consolidation is more flexible and, depending on your disruption settings, more proactive about ongoing cost optimization rather than just scale-down. See Karpenter disruption for the full consolidation and Spot-interruption handling reference.

Spot instances — a real cost lever, used deliberately

Allow Spot capacity in a NodePool, and Karpenter can use Spot instances whenever they fit the workload's requirements — significantly cheaper than On-Demand, with one condition attached: AWS can reclaim that capacity, giving a two-minute interruption notice before it does. With Karpenter's interruption handling configured, it can react to that notice, start replacement capacity, and try to drain the node before termination — but that only works safely if the workload itself is designed for disruption.

Two things matter here specifically. Run more than one replica for anything that matters — a single-replica Deployment on a Spot node that gets interrupted means real downtime until the pod reschedules elsewhere. And use Pod Disruption Budgets for critical workloads: a PDB tells Kubernetes how many replicas must stay available during voluntary disruptions like a node drain, so when Karpenter drains a Spot node, the PDB helps prevent too many replicas being evicted at once. A PDB isn't magic, though — if the underlying Spot instance is actually terminated, Kubernetes can't keep that exact node alive regardless of the budget. It makes a graceful drain safer; your application still needs enough replicas, fast startup, and real health and readiness checks to make interruption a non-event. See Kubernetes disruptions and PDBs for the minAvailable/maxUnavailable configuration. Spot is a genuine cost lever — just not one to flip on blindly for every workload. Decide it deliberately, workload by workload.

Cluster Autoscaler vs Karpenter, side by side

Area Cluster Autoscaler Karpenter
How it works Adjusts Auto Scaling Group desired capacity Provisions EC2 capacity based on pending pod requirements
Capacity model Scales pre-defined node groups Uses constraints from NodePools and EC2NodeClasses
Instance flexibility Limited to the node groups you created Chooses from allowed instance families, sizes, zones, and capacity types
Provisioning path Goes through Auto Scaling Groups Uses EC2 provisioning directly
Scale-down Removes nodes when pods can move elsewhere Uses consolidation to remove or replace empty or underused nodes
Complexity Simpler and familiar More powerful, more concepts to learn
Best fit Existing clusters or simpler ASG-based setups Newer EKS platforms needing flexible, right-sized, cost-aware provisioning

The decision isn't emotional. Cluster Autoscaler works — stable, well-understood, a valid option especially if your cluster already runs on managed node groups and ASGs. If you're designing a new EKS platform and want flexible provisioning, better instance selection, Spot support, and consolidation, Karpenter is often the better starting point. Understand both, and choose deliberately rather than by default. See the Cluster Autoscaler AWS setup for its IAM requirements and ASG integration.

Decisions to get right before you turn on Karpenter

  • IAM. Two separate roles — the controller role for Karpenter's own AWS calls, the node role for whatever it launches. Don't conflate them.
  • Where Karpenter itself runs. A small, tainted bootstrap node group, not the dynamic capacity Karpenter manages — solving the chicken-and-egg problem directly.
  • NodePool boundaries. Define instance families, capacity types, zones, and limits deliberately — this is what keeps Karpenter's flexibility from turning into unpredictable spend.
  • Consolidation pace. Match consolidateAfter to how bursty your workloads actually are, not to the most aggressive default you can find.
  • Spot. Multiple replicas and a PDB for anything critical, decided per workload — never a blanket setting.

Neither tool is really the point — the point is whether your cluster's capacity tracks what your workloads actually need, without someone babysitting node groups by hand or discovering a cost problem a month later.
