Container Registries: Docker Hub, ECR, Image Tagging, and Why "latest" Is Dangerous

By Pravin Mishra

So far we've designed the foundation of a production-grade EKS cluster — architecture, IAM, node groups. But a Kubernetes cluster doesn't run anything useful on its own — it needs container images to deploy. When the scheduler places a pod on a node, the kubelet on that node has to pull the image from somewhere. That somewhere is a container registry, and the choice of registry — plus how you tag images inside it — affects your ability to roll back a bad deployment, trace an incident to a specific code change, and keep the cluster stable.

What a container registry actually is

A container registry is a storage and distribution system for container images. Your team builds an image in a CI/CD pipeline — GitHub Actions running docker build, say — and pushes it to a registry. Your cluster then pulls that image from the registry whenever it needs to run a container. Without a registry, there's no clean way for EKS nodes running on EC2 to get an image that was built somewhere else entirely. In this course you'll see two registries regularly: Docker Hub and Amazon ECR.

Docker Hub — fine for public images, not for yours

Docker Hub is one of the most widely used public registries. When a Kubernetes manifest references nginx or postgres:15, you're usually pulling from Docker Hub — the short image name resolves there without needing a full registry URL. It's where most public images live: nginx, Redis, PostgreSQL, Node.js, and plenty more.

For public base images and learning examples, Docker Hub is completely fine. For your own application images — the ones your team actually builds and ships — the better pattern on AWS is a private registry like Amazon ECR. Docker Hub can host private images too, but then you're managing separate registry credentials inside Kubernetes. With ECR, the registry fits directly into the AWS environment you're already using: nodes pull with IAM permissions, your pipeline pushes with an AWS role, and access follows the same security model as everything else. The production pattern is simple — public images from trusted public registries, your own images from a private registry you control. Worth knowing if you lean on Docker Hub at all: it enforces pull rate limits for unauthenticated and free-tier pulls, applied per IP — which can bite a cluster of nodes sharing an egress IP.

Amazon ECR — the production registry on AWS

ECR — Elastic Container Registry — is AWS's managed container registry, and it fits EKS well precisely because it's built into the same AWS security model you're already using. Images are private by default, access is controlled through IAM, your pipeline pushes with an AWS role, and worker nodes pull using node-role permissions like AmazonEC2ContainerRegistryPullOnly. There's no separate Docker Hub token to store as a Kubernetes Secret, no separate credential to rotate, no private-registry password someone has to remember to update before it expires.

That difference matters more in production than it sounds. A team running private application images on Docker Hub usually ends up managing a token by hand — storing it as a Secret, rotating it, hoping nobody forgets. With ECR, image access is just IAM, and with the right VPC endpoints configured, nodes can pull images without touching the public internet at all. ECR isn't just "where we store Docker images" — on an AWS-based EKS platform, it's the registry that fits naturally with IAM, private networking, CI/CD, and node-level pulls. See the Amazon ECR user guide for the core concepts.

Creating an ECR repository: four decisions, not one

You can create a repository from the Console for learning and quick testing, but in production it should be treated as infrastructure — defined in Terraform, reviewed in a pull request, deployed through the same pipeline as everything else. Here's a production-style repository:

resource "aws_ecr_repository" "book_review_backend" {
  name                 = "book-review-backend"
  image_tag_mutability = "IMMUTABLE"

  encryption_configuration {
    encryption_type = "AES256"
  }

  image_scanning_configuration {
    scan_on_push = true
  }
}

Each field here is a real decision, not boilerplate. image_tag_mutability = "IMMUTABLE" enforces immutable tags at the registry level — ECR blocks any attempt to overwrite a published tag, so if someone tries to push a3f8c21 again with a different image, it simply fails. You're not relying on team discipline to enforce this; the repository makes it impossible. More on why that matters below.

encryption_type = "AES256" encrypts image layers at rest — AES-256 is ECR's default behavior anyway, but setting it explicitly makes the intent visible in code. In more regulated environments, teams may reach for KMS encryption with a customer-managed key instead, for tighter key control and audit requirements. scan_on_push = true runs ECR's basic vulnerability scan on every push, with findings surfaced in ECR for your pipeline or security process to act on — enhanced scanning via Amazon Inspector is a separate, deeper option, but basic scanning is a sensible baseline for any application image. The point isn't which of these you choose so much as choosing them deliberately instead of accepting whatever ECR does by default.

One more thing almost everyone forgets the first time: a lifecycle policy. Without one, a repository grows unbounded — a pipeline pushing an image on every commit accumulates thousands of images within months, and ECR charges per GB of storage. Old images pile up quietly until they show up as a line item on the AWS bill nobody can explain.

resource "aws_ecr_lifecycle_policy" "book_review_backend" {
  repository = aws_ecr_repository.book_review_backend.name

  policy = jsonencode({
    rules = [{
      rulePriority = 1
      description  = "Keep last 20 images"
      selection = {
        tagStatus   = "any"
        countType   = "imageCountMoreThan"
        countNumber = 20
      }
      action = {
        type = "expire"
      }
    }]
  })
}

Keep the last 20, expire everything older. For a lab, 20 is plenty; production teams typically land somewhere between 10 and 50 depending on deploy frequency. The exact number matters far less than having a policy at all. See ECR lifecycle policies, tag immutability, image scanning, and encryption at rest for the full reference on each.

Pushing an image: authenticate, tag, push

Once the repository exists, its URL follows a fixed format: <account-id>.dkr.ecr.<region>.amazonaws.com/<repository-name>:<tag> — for the Book Review App, something like 123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:a3f8c21. In the hands-on lab you push an image manually first, so the mechanics are clear before GitHub Actions automates all of it later in the course. Three steps: authenticate, tag, push.

# Authenticate
aws ecr get-login-password --region eu-west-1 \
  | docker login --username AWS --password-stdin \
    123456789012.dkr.ecr.eu-west-1.amazonaws.com

# Tag
docker tag book-review-backend \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:a3f8c21

# Push
docker push 123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:a3f8c21

Notice the tag is a commit SHA — a3f8c21 — not latest. That's not incidental, and it's the subject of the rest of this post. One more pattern worth knowing about, even though this course runs a single AWS account: in mature multi-account setups, teams often centralize ECR repositories in one account and let other accounts pull from them via repository policies — the workload account authenticates with IAM as normal, and ECR grants the pull based on the policy. See ECR cross-account repository policies if you run into that setup.

Why ":latest" is dangerous

Build an image without specifying a tag, and Docker defaults to latest. It feels natural — it sounds like it means "the most recent version." So teams push :latest, reference it in manifests, and everything looks fine — right up until they need to debug, roll back, or prove exactly which version is actually running. Here's the scenario that plays out almost identically everywhere it happens.

The app is running in production, its deployment referencing book-review-backend:latest. A developer pushes a new build, tags it :latest, and pushes to ECR — the tag now points at the new image. Your running pods aren't affected yet; they're still running whatever they pulled when they started. Then something causes a pod to restart — a node recycles, you scale up, Kubernetes schedules a new pod. If the image isn't cached on that node, it pulls :latest fresh from ECR, and gets the new build.

Now you have pods running two different versions of the same deployment, and you didn't choose that — it happened as a side effect of node scheduling. Different pods return different responses; users see inconsistent behavior depending purely on which pod happens to serve them. And then the new image turns out to have a bug, and you want to roll back — to what? There's no previous latest; you overwrote it. Your manifest has no record of what was running before. helm rollback re-applies the old release's values, but the image tag in those values is still :latest — which now points at the broken image, not the working one. The clean rollback path is simply gone, and in production that can mean real downtime spent piecing together which image was actually running before the bad push. The problem with latest isn't that the tag is technically broken — it's that it removes your ability to reason about what's running, and your ability to recover when something goes wrong.

How to tag images properly

Production image tags should be immutable and traceable. Immutable means the tag always points to the same image; traceable means you can look at a running pod and quickly work out which source commit produced it. Two common options cover most cases.

The first is a Git commit SHA — git rev-parse --short HEAD gives you something like a3f8c21, and tagging the image with it tells you exactly which commit produced it. From a running pod, to the image tag, to the exact commit, in seconds. A GitHub Actions pipeline can generate this automatically on every build. The second is a semantic version like 1.4.2 — more human-readable, easier to communicate across teams for a formal release. In practice, many teams use both: release 1.4.2, but keep the commit SHA as build metadata alongside it. The exact naming convention matters less than the underlying rule: never use a moving tag for a production deployment — use a tag that points to exactly one build.

SHA=$(git rev-parse --short HEAD)

docker tag book-review-backend \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:${SHA}
docker push 123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:${SHA}

Your Kubernetes manifest then references that exact tag:

spec:
  containers:
    - name: book-review-backend
      image: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/book-review-backend:a3f8c21
      imagePullPolicy: IfNotPresent

imagePullPolicy: IfNotPresent is worth noticing specifically — it pairs naturally with immutable tags. If a node already has that exact image cached, Kubernetes reuses it instead of pulling again, since the tag is immutable and the cached image and registry image are guaranteed to represent the same build. That's faster pod startup, less unnecessary network traffic, and predictable behavior. With :latest, the situation flips: Kubernetes treats it as a moving tag and defaults the pull policy to Always, so the kubelet checks the registry on every container start — slower, and worse, it makes it genuinely hard to know which build is actually running at any given moment. See the Kubernetes imagePullPolicy reference for the full default-behavior rules.

The production rule: never overwrite a published image tag. Once a3f8c21 is pushed, that tag should point to that exact image forever — if you need to fix something, build a new image with a new tag. This is exactly what ECR tag immutability enforces at the registry level: with it enabled, an attempt to push a different image under an existing tag is simply rejected, no discipline required.

Decisions to get right before you push your first image

  • Registry choice. Trusted public images from Docker Hub; your own application images from a private registry like ECR.
  • Repository config. Decide tag immutability, encryption, and scan-on-push explicitly for every repository — don't inherit whatever the default happens to be.
  • Lifecycle policy. Every repository needs one from day one. The exact retention count matters less than having a policy at all.
  • Tagging. Commit SHA or semantic version — never a moving tag — for anything deployed to production.
  • Pull policy. IfNotPresent with immutable tags for faster, predictable startup; avoid relying on :latest's implicit Always behavior.

None of this is really about Docker mechanics — it's about whether you can answer "what's actually running in production right now, and can I get back to what was running an hour ago" without guessing. That's exactly the kind of production judgment DMI's daily grading loop is built to develop.
