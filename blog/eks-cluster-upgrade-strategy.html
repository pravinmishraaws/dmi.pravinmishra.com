EKS Cluster Upgrade Strategy: Control Plane, Add-Ons, and Node Groups

By Pravin Mishra

We've now covered the foundation of a production-grade EKS cluster — architecture, IAM, node groups, and images in ECR. Here's something engineers often skip when first setting up a cluster, and it's one of the things that bites teams hardest in production: a cluster isn't something you create once and forget. You have to upgrade it, regularly — and if you leave it on an unsupported version long enough, AWS can eventually update the control plane for you, on a timeline you didn't choose.

Why you can't just leave the cluster running

Kubernetes ships a new minor version roughly every four months. EKS gives each one a standard support window, then extended support, and once that full lifecycle ends, AWS can automatically update the control plane whether you're ready or not. The practical point: you get time to plan, but you shouldn't wait until AWS is planning the upgrade for you. A forced upgrade on a cluster you haven't prepared is exactly how production incidents happen — deprecated APIs your workloads depend on stop working, add-on versions break, and you're scrambling on a timeline you never chose.

Stay close to current, and you plan upgrades on a predictable cadence — often about once a year, depending on your version and its support window. Teams that treat it as a scheduled item handle it smoothly. Teams that ignore it until AWS sends a deprecation notice are the ones with weekend incidents.

The three steps — and the one most people skip

Most people think an EKS upgrade is two steps. It's actually three, and the one that gets skipped is exactly where things break.

Step 1 — upgrade the control plane

This part is simple: change the Kubernetes version in your Terraform config.

module "eks" {
  kubernetes_version = "1.30"   # was "1.29"
  ...
}

Commit, open a pull request, let Terraform apply it through your pipeline. AWS handles everything on its side — the API server, etcd, the scheduler. Your worker nodes stay on 1.29, and your application keeps running throughout. The control plane upgrade itself takes roughly 20 to 30 minutes; you may see brief API-server interruptions during that window, but already-running pods generally keep running.

Step 2 — upgrade your add-ons (the one everyone skips)

This is the step that causes the subtle, hard-to-diagnose failures. Your cluster runs several managed add-ons — VPC CNI, CoreDNS, kube-proxy, the Pod Identity agent — and each one has its own version with its own compatibility matrix against Kubernetes versions.

Skip this step, and here's what actually happens: your control plane moves to 1.30, your nodes move to 1.30, but the VPC CNI is still on an older version that isn't the right match for the new cluster version. What you see next doesn't look like an upgrade problem at all — pods failing to get IPs, DNS behaving unpredictably, traffic looking intermittent. Teams routinely spend hours debugging this as a networking issue before realizing it's an add-on version mismatch left over from the upgrade.

The fix is to manage add-on versions as pinned Terraform variables, one set per environment:

# terraform.tfvars
EKS_version              = "1.30"
coredns_addon_version    = "v1.11.4-eksbuild.2"
cni_addon_version        = "v1.19.0-eksbuild.2"
kube_proxy_addon_version = "v1.30.3-eksbuild.5"

When you upgrade, bump these alongside the Kubernetes version in the same pull request, applied through the same Terraform pipeline as everything else. Nobody runs ad-hoc CLI commands against production to patch an add-on version. Before bumping anything, check which add-on versions are actually compatible with your target Kubernetes version:

aws eks describe-addon-versions \
  --kubernetes-version 1.30 \
  --region eu-west-1

AWS also publishes the full compatibility matrix in the EKS add-ons documentation — check it before every upgrade, not just the first one.

One more detail that's easy to miss but matters specifically during upgrades: in the Terraform EKS module, you can tell an add-on to install before_compute — before any nodes launch.

addons = {
  cni = {
    name           = "vpc-cni"
    addon_version  = var.cni_addon_version
    before_compute = true
  }
  kube-proxy = {
    name           = "kube-proxy"
    addon_version  = var.kube_proxy_addon_version
    before_compute = true
  }
}

Why this matters: when nodes are replaced during an upgrade, they need to join a cluster where the VPC CNI is already at the correct version. If the updated CNI isn't in place before new nodes start joining, pods get stuck in Pending with networking errors that are confusing to trace back to the real cause. before_compute = true enforces the ordering — CNI and kube-proxy are ready before any node touches the cluster. This matters during initial cluster creation too, and it carries over cleanly into the upgrade workflow, since your Terraform plan updates the add-ons before replacing compute. Still worth reviewing the plan directly, so you can see that ordering happening rather than assuming it.

Step 3 — upgrade the node groups

Only after the control plane and add-ons are updated do you touch the nodes. With managed node groups, AWS performs a rolling replacement — drain one node, terminate it, launch a replacement on the updated Kubernetes version, wait for it to be healthy, move to the next. Your application can stay up through this if you have enough replicas, healthy capacity, working readiness checks, and disruption budgets set up correctly — none of that is automatic, it's the result of decisions you made when you sized and configured the deployment.

In a Terraform-managed setup this is another variable bump and apply, same as the rest. In the lab, with eksctl, you can run it directly:

eksctl upgrade nodegroup \
  --name bootstrap \
  --cluster book-review \
  --kubernetes-version 1.30 \
  --region eu-west-1

See updating a managed node group for the full rolling-replacement and drain behavior.

You can't skip minor versions

One hard constraint to know before you run any upgrade: you can't jump from 1.28 straight to 1.30. It has to be 1.28 → 1.29 → 1.30, each step going through all three phases above. EKS in-place upgrades are designed around moving one minor version at a time — that's what keeps API removals, component version skew, and add-on compatibility manageable. Jump further than that, and the path is unsupported; you can hit removed APIs or unsupported component combinations with no clean way through.

The practical consequence: let a cluster fall two or three versions behind, and you're not facing one upgrade, you're facing a chain of them, each one needing its own verification before the next starts. What should be a routine job becomes a multi-week project done under pressure. One upgrade a year is manageable. Three of them back-to-back in a panic is not. See the Kubernetes version skew policy for exactly why skipping isn't supported, and the EKS Kubernetes release calendar to check support end dates before you plan the next one.

Always upgrade stage first, never production directly

There's one more habit that separates teams who handle upgrades calmly from the ones who have incidents: never upgrade production directly. With the same Terraform config deployed to stage and production through separate tfvars files, you bump the Kubernetes version and every add-on version in the stage tfvars first.

# stage.tfvars
EKS_version              = "1.30"
coredns_addon_version    = "v1.11.4-eksbuild.2"
cni_addon_version        = "v1.19.0-eksbuild.2"
kube_proxy_addon_version = "v1.30.3-eksbuild.5"

Apply to stage, watch the metrics, verify your application, Helm charts, and any ArgoCD-managed workloads actually work on the new version. Only once stage is stable do you make the identical version bumps in the production tfvars.

# prod.tfvars
EKS_version              = "1.30"
coredns_addon_version    = "v1.11.4-eksbuild.2"
cni_addon_version        = "v1.19.0-eksbuild.2"
kube_proxy_addon_version = "v1.30.3-eksbuild.5"

Same versions, no guessing — you already know exactly what Terraform will do to production, because you watched it happen on stage first. This isn't a large-team-only process either: even running the cluster solo, this discipline pays for itself. An upgrade that fails on stage at 10am is an inconvenience. The identical failure on production at 10am is a customer-facing incident.

Decisions to get right before your next upgrade

  • Cadence. Plan an upgrade roughly once a year, matched to your version's support window — don't wait for AWS's deprecation notice to force the timeline.
  • Order. Control plane, then add-ons, then node groups. Never node groups first, and never skip the add-on step.
  • Add-on versions. Pin them as Terraform variables, bump them in the same PR as the Kubernetes version, and check the compatibility matrix before every bump.
  • Add-on ordering. Set before_compute = true on VPC CNI and kube-proxy so they're correct before any node joins.
  • Version jumps. One minor version at a time, always — a cluster left several versions behind turns one upgrade into a chain of them.
  • Rollout order. Stage first, verified, then the identical version bumps to production. Never the reverse.

One practical habit worth carrying into the lab itself: when you're not actively working on the cluster, delete it — eksctl delete cluster --name book-review --region eu-west-1 --wait. About 15 minutes to delete, 15 to recreate; there's no reason to pay for idle nodes while you're still learning.

None of this is really about Kubernetes version numbers — it's about whether an upgrade is a scheduled, boring, reviewable event or an unplanned one forced on you at the worst possible time. That's exactly the kind of production judgment DMI's graded weekly loop is built to develop.
